## 1. Purpose and Scope

This plan defines how the organization detects, triages, contains, and recovers from a security or availability incident affecting the Bookstore platform described in [`../ARCHITECTURE.md`](../ARCHITECTURE.md) — the EKS microservices application, its RDS database, the monitoring stack, and the Alertmanager-triggered AIOps RCA pipeline. It satisfies SOC 2 CC7.3/CC7.4 (incident response), ISO/IEC 27001:2022 A.5.24–A.5.26 (incident management), and PCI DSS v4.0 Req 12.10 to the extent applicable — see [`INFORMATION_SECURITY_POLICY.md`](INFORMATION_SECURITY_POLICY.md) Section 5 for this system's PCI scoping conclusion (no cardholder data environment exists, so PCI's incident-response requirements around cardholder data specifically do not apply).

## 3. Severity Classification

Severity in this plan is tied directly to the two Alertmanager severity labels already in use in this stack (`terraform/modules/monitoring-ec2/user-data.sh.tftpl`'s `alertRules`/`route` blocks), not an invented separate scale:

| Plan severity | Alertmanager label | Examples from this stack's real alert rules | Notification |
|---|---|---|---|
| **Sev-1 / Critical** | `severity: critical` | `HighErrorRate` (5xx ratio > 5%), `KubeStateMetricsDown`, node `up == 0` for 5m | Routed to the `critical-webhook` receiver, `repeat_interval: 1h` — fires the RCA webhook and an SES email every hour until resolved |
| **Sev-2 / Warning** | `severity: warning` | `HighCPUUsage` (>80%, 10m), `HighMemoryUsage` (>85%, 10m), `PodCrashLooping`, `HighPodCPUUsage`/`HighPodMemoryUsage`, `HighRequestRate` | Routed to the `default-webhook` receiver, `repeat_interval: 6h` |
| **Sev-3 / Informational** | (no Alertmanager label; e.g. a failed Dependabot PR, a non-blocking CI finding) | — | No automated paging; triaged during normal working hours |

A security-specific incident (credential leak, unauthorized access, suspected compromise) that does not correspond to any firing Prometheus alert is classified **Sev-1 by default** regardless of whether Alertmanager ever labels it — the mapping above covers availability/performance alerts, not every incident type. Alertmanager's `inhibit_rules` (same file) suppress a `warning` for an `alertname`+`instance` pair that already has a matching `critical` firing, so triage should always check for a related Sev-1 before spending time on an apparently-standalone Sev-2.

| Source | What it surfaces | Where to look |
|---|---|---|

| Gitleaks | A secret committed to the repository | GitHub Actions run log for the `secret-scan` job; also GitHub's own secret-scanning alerts if enabled |
| Trivy | A CRITICAL/HIGH CVE in a pushed container image or a Terraform IaC misconfiguration | GitHub Security tab (SARIF upload, `.github/workflows/ci-cd.yml`) |
| CloudTrail | Anomalous or unauthorized AWS API activity | The `bookstore-cloudtrail-<account-id>` S3 bucket (`terraform/cloudtrail.tf`) — see Section 5.4 below; **no automated alerting on CloudTrail events exists yet** (see Section 8, gap G-3) |
| A human report | Anything not caught automatically | [`../SECURITY.md`](../SECURITY.md)'s private vulnerability reporting process |

## 5. Containment — concrete steps for this stack

These steps are written against the real components in this system, not generic advice. Every action below should be logged by the Scribe with a timestamp.

### 5.1 Revoking a compromised pod's or service's access

Every microservice reads its database credentials and other secrets through an `ExternalSecret` resource, synced from AWS Secrets Manager by the External Secrets Operator via a shared, cluster-wide IRSA role scoped to `/bookstore/*` (see [`../ARCHITECTURE.md`](../ARCHITECTURE.md#secrets-flow-and-the-bug-that-used-to-break-it)). To cut a compromised pod off from Secrets Manager:

1. Identify the affected namespace/service (`catalog`, `user`, `order`, `notification`, or `gateway`).
2. Delete or scale down the affected Deployment first (`kubectl scale deployment/<name> -n <namespace> --replicas=0`) to stop it from acting on credentials it already holds in memory.
3. Because the IRSA role is shared cluster-wide rather than per-service (a documented, accepted-risk simplification — [`../ARCHITECTURE.md`](../ARCHITECTURE.md#secrets-flow-and-the-bug-that-used-to-break-it)), there is no way to revoke *only* the compromised service's access to Secrets Manager without affecting every other `ExternalSecret` in the cluster. The available options, in order of severity:
   - Rotate the specific secret(s) the compromised service could read (Section 5.2) — this invalidates what the attacker captured without taking down other services.
   - If the compromise is believed to be at the ServiceAccount/IRSA level rather than the pod's captured secret value, remove or restrict the `external-secrets-sa` ServiceAccount's IRSA annotation (`eks.amazonaws.com/role-arn`) in `terraform/modules/eks-addons/external-secrets.tf`, which cuts off ESO's ability to sync *any* secret cluster-wide until reissued — a last resort given the blast radius, but sometimes the correct one.
4. Delete the pod's `ExternalSecret`-derived Kubernetes `Secret` object directly if immediate, service-scoped denial is needed and a full IRSA change is too slow: `kubectl delete secret <secret-name> -n <namespace>` — ESO will attempt to recreate it on its next sync interval, so this is a delay, not a permanent block, unless combined with scaling the Deployment to zero first.

### 5.2 Rotating `/bookstore/*` secrets

```bash
# Example: rotate the RDS admin credential immediately, outside the normal
# rotation schedule described in INFORMATION_SECURITY_POLICY.md Section 4.5
aws secretsmanager rotate-secret --secret-id /bookstore/db-credentials

# Or, if no rotation Lambda is deployed (enable_rds_secret_rotation is off
# by default -- see terraform/rds-secret-rotation.tf), rotate manually:
aws secretsmanager put-secret-value --secret-id /bookstore/db-credentials \
  --secret-string '{"DB_USERNAME":"...","DB_PASSWORD":"<new-password>","DB_HOST":"..."}'
```

After a manual rotation, every pod holding the old value via a mounted `ExternalSecret` needs a rolling restart to pick up the new one (ESO does not automatically restart consumers on a secret change): `kubectl rollout restart deployment -n <namespace>`.

The same pattern applies to `/bookstore/grafana-admin`, `/bookstore/monitoring-basic-auth`, `/bookstore/jwt-secret`, and `/bookstore/claude-api-key` — rotate the value, then restart whatever consumes it (the monitoring EC2's Docker Compose stack for the first two, `api-gateway` for the JWT secret, the RCA Lambda for the Claude key — Lambda picks up a new Secrets Manager value on its next cold start, or immediately if the deployed code's in-memory cache is cleared by a redeploy).

### 5.3 Isolating a compromised node or service at the network layer

`NetworkPolicy` objects already restrict east-west traffic to `gateway`-namespace-only ingress for `catalog-service`/`user-service`/`order-service` (see [`../ARCHITECTURE.md`](../ARCHITECTURE.md)). To further isolate a specific compromised pod during an active incident, apply a deny-all `NetworkPolicy` scoped to that pod's labels, or cordon and drain the node it is running on (`kubectl cordon <node>` then `kubectl drain <node> --ignore-daemonsets`) to stop new pods from scheduling there while the investigation continues.

### 5.4 Pulling an audit timeline

CloudTrail (`terraform/cloudtrail.tf`, new this session) is the first place to look for account-level activity — who called which AWS API, when, from where. It is a multi-region trail with log file validation, writing to an Object-Lock-protected S3 bucket, so the timeline it provides cannot have been altered by an attacker who gained account access, including root. Practical query pattern:

```bash
aws cloudtrail lookup-events \
  --start-time "<incident-start-minus-1h>" \
  --end-time "<now>" \
  --lookup-attributes AttributeKey=Username,AttributeValue=<suspected-principal>
```

For events older than the 90-day `lookup-events` API window, pull the raw log files directly from the `bookstore-cloudtrail-<account-id>` S3 bucket under `AWSLogs/<account-id>/CloudTrail/`.

For in-cluster activity, Loki (14-day retention — `terraform/modules/monitoring-ec2/user-data.sh.tftpl`'s Loki config) and each service's own structured JSON application logs (winston) are the next source; anything older than 14 days is not recoverable from Loki, only from whatever the RCA pipeline already captured into DynamoDB for an alert that happened to fire in that window.

## 8. Known Gaps

- **G-1 (MFA):** human AWS console/IAM access has no enforced MFA requirement yet — see [`INFORMATION_SECURITY_POLICY.md`](INFORMATION_SECURITY_POLICY.md) Section 3.3. Relevant to containment because an incident involving a compromised human credential currently has a lower bar to clear than it should.
- **G-2 (shared IRSA blast radius):** Section 5.1 above cannot cleanly revoke a single service's Secrets Manager access without affecting the whole cluster — a known, accepted-risk simplification, not remediated in this pass.
- **G-3 (no CloudTrail alerting):** CloudTrail now captures the audit trail, but nothing currently parses it for anomalous activity in real time — it is a forensic source today, not an early-warning system. [Action: consider CloudTrail → EventBridge → the existing Alertmanager/RCA webhook path, or a dedicated tool, as a future enhancement.]
- **G-4 (no formal escalation/paging tool):** Section 2's escalation path is undefined beyond the existing SES email/RCA dashboard notification. [Decision: adopt a paging tool once the team grows beyond a single maintainer.]
